# Changelog

All notable changes to the Agent Toolkit plugin are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

> **Update discipline:** this file must be updated on every version bump. `/release` does it for you; see `## Releasing` and `## Release Files` in `CLAUDE.md` for what it rewrites.

## [0.9.1] — 2026-08-17 — "Whole Field"

v0.9.0 documented this bug in the same paragraph that shipped it, and said it could not ride along. It rides now.

The prune matched with `grep -v -F "$l1"`, which matches a substring of the **whole row** — so a legal, non-empty locator deleted every row that merely contained it. Measured on a two-row herdr ledger: pruning `w9:p3` took `w9:p30` with it and left **0 rows, exit 0**. That is the empty-variable catastrophe the `[ -n … ]` guard was written to prevent, reached with a perfectly valid locator, so the guard never fires and nothing anywhere reports a fault. cmux was safe from it by accident — its uuids are fixed-width and cannot prefix-collide — while herdr's pane ids climb and are never reused, so the collision arrives as soon as a server session has created ten-plus panes.

### Fixed

- **The prune matches the name as a whole field**, `awk -F'\t' -v k=1 -v want="$name"`, not a substring of the line. Column 1 is the row key the watcher already reads and every `owned.py` lookup already resolves through, so keying the prune on anything else was matching a field the rest of the skill does not treat as the identity. It is also host-free, which retires the cross-host reasoning the locator form needed.

### Changed

- **Two hazards documented for three releases were properties of `grep`, and are now gone.** Both re-measured on the new line, and the skill says so explicitly so that a later editor does not restore a warning that no longer describes anything: joining with `&&` used to skip the `mv` on the last row, because `grep` exits 1 when it selects nothing — `awk` exits 0 either way; and an empty variable used to install *nothing* over the whole file — an empty `want` keeps every row whose column 1 is non-empty, and the fixture survives intact. The `;` stays because it is unconditionally correct and free; the `[ -n "$name" ]` guard stays because an empty name means the loop variable did not survive a `Bash` call, which is worth refusing rather than treating as a no-op.
- **Smoke check 4 gained a fourth direction and a control.** `D` prunes one of `w9:p3` / `w9:p30` and requires the other to survive; `D-control` replays the old `grep` on the same fixture and must destroy both rows while exiting 0. A `D-control` that returns one row is a FAIL of the *check* — it means the fixture stopped reproducing the bug, so `D` is asserting nothing. Directions `A` and `B` kept their commands but had their premises inverted by the fix, and now say what they still prove rather than what they used to.

## [0.9.0] — 2026-08-17 — "Postmark"

**Breaking: the ledger is seven columns.** An older session's skill text reads a new ledger, hits `awk 'NF && NF!=6'`, prints `columns=7` and refuses to spawn. That is reachable without anyone erring — skill text is snapshotted at session start while `lib/*.py` is read fresh on every call — so a supervisor already running when this lands keeps the old check. Quit and restart it; there is nothing to migrate, because teardown deletes the ledger anyway.

Columns 2 and 3 are host locators whose meaning the host file defines — cmux writes a surface uuid and a pane uuid, herdr writes a pane id and a terminal id — and **nothing in the row said which host wrote it.** Measured 2026-08-17: one cmux supervisor held two cmux workers and one herdr worker in one ledger. Everything host-independent worked, and that is most of the skill: `owned.py` joins on columns 5 and 6, so addresses, status, cwd and the pid pin all resolved across hosts, and the watcher reads column 1 only. Teardown did not. It resolves *every* row's locator with *one* host's resolver, so the herdr row came back unresolvable, was read as "the user already closed it", and would have been pruned — a leaked tab, reported as a clean finish. The run that found this had to close that tab by hand.

Recording the host is what makes the two cases distinguishable, and the same column then answers a question the old format could not even ask: *may* this supervisor close that row. The two hosts differ, so the answer is asymmetric rather than symmetric — see below.

### Added

- **Column 7 names the host that wrote the row**, derived in the setup block from the same expression §0 uses to pick the host file, so the tag and the file choice are one decision rather than two that can disagree. That matters precisely because a herdr pane inherits the herdr *server's* environment: in a herdr-under-cmux session both hosts' variables are live and a hand-copied literal would be invisibly wrong.
- **The teardown table replaces one silent branch with four explicit ones.** A row tagged this host resolves as before. A row tagged the other host is closed when that host's close needs nothing from the environment, and refused with a full report when it does. A row that is empty or unrecognised is never closed and never pruned. Every line now carries `l1`, `l2` and the resume id whether or not it will be closed, because "Finish the run" deletes the ledger unconditionally and nothing on disk names those slots afterwards.
- **Each host file states, in its own close section, whether its close is reachable from a supervisor sitting in the other host** — so `SKILL.md` never has to assume symmetry, and stays free of terminal commands. cmux → herdr works (`herdr tab close` takes an explicit id); herdr → cmux does not, because `cmux close-surface` needs `--workspace`, whose value inside herdr is the inherited-and-wrong one.

### Fixed

- **`cmux.md`'s pane-reuse scan is scoped to cmux rows.** It read column 3 of every row, so a herdr terminal id was offered as a pane candidate. Harmless only because it intersected against live cmux panes.
- **Both host files stopped teaching "unresolvable means already closed."** cmux exited 0 with *"already gone; closing nothing"* and herdr said *"drop the row and close nothing"* — true for a slot the user closed, false for a locator this supervisor merely cannot read, and false again for herdr's own explicitly-unmeasured pane-id durability across a server restart.

### Changed

- **Column 6 holds a literal `-` before the pid is pinned, never an empty field.** This is not tidiness and it was measured, in both zsh and bash: an empty *trailing* column is stripped, but appending column 7 makes it *interior*, and adjacent tabs collapse under IFS field splitting — so `pid` receives `cmux` and `host` receives nothing. `awk` still counts `NF=7`, so the format check cannot catch it. Every worker would have read host-unknown between its row being written and its pid being pinned, and rows that never pin — the 60-second timeout branch — would have stayed that way forever, which is exactly the set of workers the column was added to protect.
- **The variable is `SPAWN_HOST`, and `HOST` was a trap.** zsh presets `HOST` to the machine's hostname; bash does not. A block that failed to re-derive it — the ordinary failure this file warns about on every page, since shell state dies with each call — passed its own non-empty guard under zsh and wrote `Mikes-MacBook-Pro-M5.local` into column 7. That row then passes the format check and lands on the "word you do not recognise" branch: a leaked slot reported as a clean finish, re-entered through the guard meant to prevent it.
- **Three shipped docstrings described a six-column ledger**, the guard's by printing the schema line verbatim. No behaviour changed: every reader is length-guarded, `owned.py`'s pid re-join is gated on `.isdigit()` (false for `-` exactly as for the empty string), and `occupant.py` reads `-` as a stranger the same way it read the empty field.

## [0.8.1] — 2026-08-17 — "Hearsay"

Mid-run, an orchestrator relayed its user's standing instruction to a running worker as a peer `SendMessage` — *you may self-approve your remaining gates*. The worker read it and **raised its own gate rather than acting on it**, saying it could not treat a peer's claim about the user as the user's approval. It was right, and that is the finding: an authorization delivered over messaging is not merely late, it is *correctly refused*, and the refusal costs a gate that would not otherwise exist.

`SKILL.md` already contained the answer — *use keys "whenever the worker must act on the user's own authority"* — as a subordinate clause at the end of a sentence about slash commands, in a table about delivery mechanics. Every other hazard in that file is documented by its measured failure mode; this one was documented as a channel preference. The consequence was nowhere.

What makes it decidable is an asymmetry the same worker stated unprompted, having accepted two other instructions from the same message without challenge: **those narrowed its scope rather than expanding it, so they needed no separate authorization.** A peer may restrict what a worker does and supply facts it can check for itself; a peer may never widen what it may do. The practical consequence is that gate policy belongs in the kickoff text, where it is part of the job the user's own launch created — 1 of 1 worker told mid-run raised the gate, and 0 of the 2 launched with the policy in their kickoff did.

Documentation only: four insertions, no measured sentence reworded, no heading renamed, and no behavioural change to any script or hook.

### Changed

- **`SKILL.md` states the rule that decides it**, in a new subsection closing the two-channel section: a peer message may **narrow** a worker's scope and supply corrections it can verify, and may never **widen** it — approve a gate, grant a permission, or assert what the user said as grounds for acting. It also records that nothing enforces this: the `SendMessage` guard decides on the target address alone and never reads the message body, so a send to a worker you really did spawn passes in silence however it is worded. The worker's own judgement is the only thing in the path.
- **Gate policy is named as part of the kickoff spec.** "Send the task" already demanded the whole spec, the literal `uds:` reply address and what *done* means; it now names the worker's gate policy — whether it may approve its own checkpoints or must stop and ask at each one — because a policy that arrives later arrives from a peer, which is exactly what a worker is right to refuse.
- **The pre-selection warning now cuts both ways.** "Answer a blocked worker" recorded one direction of the miscount — an extra `down` on the folder-trust gate selects "No, exit" and kills the worker — and generalised from it that the safe option is usually pre-selected. Measured 2026-08-17, the inverse: on a gate offering *"1. Keep asking me at each gate"* (pre-selected) and *"2. You approve them — run to the draft PR"*, a reflexive `enter` would have chosen the opposite of what the user had just asked for. Unlike the extra `down`, it kills nothing and errors nothing — the run continues, looking healthy, under a policy nobody chose. "Pre-selected" predicts the *conservative* option, which is not the same as the one carrying the user's answer.

## [0.8.0] — 2026-08-14 — "Turnstile"

For two releases this file and the README described **the enforcement hook** — the thing that stops a `SendMessage` landing in a session a run cannot prove it spawned — and no reader could obtain it. It was untracked, in no repository, wired by absolute path into one machine's `settings.json`. The skill hedged accordingly (*"a `PreToolUse` hook **may be** enforcing this"*), the smoke test called its absence "not a FAIL", and both were telling the truth about a component that was documented as if it shipped.

It ships now, and shipping it is what exposed the two defects below. Both were measured on the file as it stood, both are the same shape — an environment variable trusted without normalising it — and neither is visible from inside a working setup, which is why two releases of using it daily never surfaced them.

**A hook is not a skill, and the difference is consent.** A skill runs when a model chooses it; a hook runs in every session of everyone who installs the plugin, including everyone who never spawns anything, and there is no per-hook off switch — disabling it means disabling the skill. That asymmetry is why the guard now scopes *itself* out rather than relying on the installer to want it.

### Added

- **`hooks/hooks.json` and `hooks/spawn-agent-guard.py` — the guard ships.** `PreToolUse` on `SendMessage`, auto-discovered when the plugin is enabled, needing no `plugin.json` field. It never returns `allow`: it stays silent or it asks, so it can only ever add a confirmation, never remove one. It **self-scopes** — with no `.owner` sidecar anywhere in the spawn ledger directory it returns before it looks at the target, which is the state in which it could only ever add prompts and never grant anything. That is a condition rather than a milestone: teardown removes the sidecar, so a machine between runs is out of scope again.
- **Regression cover for both defects below**, in smoke check 3b, written in the ask-versus-silence direction so a fixture can never grant. The `TMPDIR` case asserts that the two cwds *agree*, not that either is silent — whether `/tmp/spawn-agent` holds sidecars is a property of the machine and pinning it would fail a correct guard elsewhere.

### Fixed

- **The guard prompted on machines that had never spawned anything.** Measured: with no ledger directory at all, a payload naming any live local session returned `ask` — so anyone installing the marketplace for the spawn skill and never running it got a confirmation prompt on a built-in tool, for their own second tab, with no way to switch it off short of removing the plugin. It now returns immediately in that state.
- **An empty `TMPDIR` made the ledger directory relative, and then it was the current directory.** `os.environ.get("TMPDIR", "/tmp")` returns `""` for a variable that is set and empty — the default only applies when the key is absent — so the path became the bare `spawn-agent`. Measured with the same payload and profile, varying only the cwd: from a directory containing `spawn-agent/<slot>.tsv` and its `.owner`, the guard **passed through silently**; from a sibling directory it asked. Files committed to a repository would have granted message-ownership of a live session. The directory is now absolute or refused, and the globs are `glob.escape`d, since metacharacters in `TMPDIR` disarmed it the same way.
- **`os.kill(pid, 0)` is not a liveness probe on Windows** — it calls `TerminateProcess`, and the session registry is pid-keyed, so the guard would have walked live pids and killed them. It now returns on any non-POSIX platform. Unmeasured, and the code says so; there is no Windows host here, and one line against destroying a stranger's processes is worth taking on the documentation alone.

### Changed

- **The skill states what is now true, without overstating it.** "May be enforcing this" becomes enforcement that ships — qualified by the two things that remain true: a user can disable the plugin, and the guard is out of scope whenever no sidecar is present. `hosts/herdr.md` gains the counterpart to cmux's warning that the hook cannot see the host's own task-delivery channel, sharpened because `herdr agent prompt` is addressed by **bare name** and its occupant check appears later in the file than the command it guards — document order is not running order.
- **The smoke test stopped grading its own homework.** Check 3b resolves the guard from the plugin root rather than a home-directory path, and its absence is a FAIL now that it ships. Its structural assertions were mutation-tested rather than trusted: the line whose prose called it "the assertion with teeth" printed **nothing and exited 0** when the command named no `${CLAUDE_PLUGIN_ROOT}` path — precisely what a bad merge restoring the old absolute path produces — and the timeout check accepted `10000`, the mistake the paragraph beneath it warns about. Both now fail, and a `PASS on exactly` block makes a missing line visible rather than absent.
- **`README.md` and the two manifest descriptions say that installing arms a hook**, because "skills for running work in visible sessions" no longer describes everything the plugin does to a session. The README also carries the caveat that a hook inherits the `claude` process's environment rather than a login shell's, so an interpreter arriving via `pyenv` or `asdf` may not resolve on a GUI-launched host — unfixable in `hooks.json`, where an absolute path would be wrong everywhere else.

## [0.7.1] — 2026-08-14 — "Notary"

v0.7.0 made ownership something a run **mints** — a six-column ledger and a one-line `.owner` sidecar beside it. It did not make the proof *required*. `owned.py` read a missing sidecar as `except OSError: pass` and resolved rows anyway, so a ledger that could prove nothing about anything in it still handed out working `uds:` addresses — for workers whose every `SendMessage` the enforcement hook was already refusing, in both directions. And `SKILL.md`'s own diagnostic sent the blocked supervisor to `owned.py`, which reported nothing wrong.

**That state is reachable without anyone erring, which is why it shipped.** Skill text is snapshotted at session start while `lib/*.py` is read fresh on every call, so a supervisor upgraded mid-run was served pre-sidecar instructions, wrote valid six-column rows by hand, and never wrote a sidecar. Found on a live run of the plugin against itself, not by reading it. Nothing that worked correctly stops working here: what now refuses was already being refused one layer up, silently and with no way to find out why.

### Fixed

- **A ledger with no `.owner` beside it is now exit 5, and it is a verdict on the ledger rather than on a row** — every field refuses alike, because a file with no sidecar proves nothing about anything in it. A zero-byte and a whitespace-only sidecar read the same as an absent one. Exits 1/2/3/4 are unchanged wherever a sidecar exists, and a *present* sidecar that `me.py` cannot check still falls through, so fixture profiles and unusual profile layouts keep working. The stderr line carries the repair with the real sidecar and `me.py` paths filled in, which is what makes the refusal actionable at the one tool the skill sends a blocked supervisor to.
- **A missing ledger is exit 2, not exit 5.** `owned.py ""` is the ordinary way in — a `Bash` call's shell state does not outlive the call, so a block that forgets to re-derive `$LEDGER` passes an empty one, and it rendered as two invisible spaces in the message. It was being answered as a *missing sidecar*, whose repair line ended in a bare relative `.owner`: one paste from dropping that file into whatever directory the caller happened to stand in, normally the user's repo. A path with no file behind it has no rows, so refusing there cannot re-open the hole exit 5 closes.
- **The setup block had the same hole from the other side.** `[ -s "$OWNER_FILE" ]` is false for absent and empty alike, so rows with no sidecar fell past the ownership test and the unconditional stamp below made them this session's. Reproduced end to end: run A leaves a sidecar-less ledger, run B stamps its own id, and `owned.py` then resolves run A's worker for run B at exit 0. It now refuses and names the file — which is what the sidecar paragraph already claimed it did.
- **Three consumers of the exit codes read a refusal as something else.** The cleanup loop turned it into a death: measured on two ledgers identical but for the sidecar and naming the same live session, `registry=idle resume=1111…` became `registry=gone resume=none`, which the bullet beneath it reads as "died mid-stage, lead with those" — and `occupant.py` does not stop the close, because it joins on the pinned pid and never reads `.owner`. A whole ledger reading `gone` with `resume=none` is now named as the exit-5 signature. The readiness loop's message said the worker "resolves to a session this run did not spawn", which is precisely wrong for 5 and contradicts the paragraph this release adds; it now carries the code and defers to the stderr above it. The `status`/`waitingFor` discriminator enumerated the causes of a blank result without 5 among them.
- **The smoke test's enforcement check could not see the decision it asserts** — a regression this work introduced into the release gate before it was caught. It checked that the guard's output was non-empty: the real guard answers `ask` in 356 bytes and a stub with `allow` swapped in answers in 358, so both passed a block whose own prose two lines down calls the second a FAIL. It now prints and asserts the decision string. Both halves also skip for real when no guard is installed, rather than announcing a skip and then running the missing hook anyway.

### Changed

- **The README taught the model this release enforces the opposite of.** "Nothing has to be pre-assigned: no `--session-id`, no `uuidgen`" is the first paragraph a reader meets, and its ledger bullet gave a TSV row with no column count and no mention of the sidecar. `git log -1 -S` dates both to v0.6.3: v0.7.0 changed exactly one line of that file, the `Latest:` line, so the breaking change shipped with the README describing what it broke. This reaches anyone installing from a `github` source, where the cached payload is what gets served.
- **Check 3b is a regression test rather than a description of one.** It now runs seven fixtures — `nosidecar`, `ambiguous` and `noledger` are new — and reverting `owned.py` flips exactly one line of the matrix, `nosidecar` back to 0 with a working address printed under it. The three pre-existing fixtures gained sidecars, without which they would stop at the new check and never reach the assertion each exists to make. `ambiguous` closes a gap the old comment promised and never delivered: it advertised two records for the more-than-one-match case, wrote one, and left exit 4 — a HARD STOP path — asserted nowhere.

## [0.7.0] — 2026-08-13 — "Deed"

A run could drive any live session on the machine. Workers were resolved by **name**, and a name identifies a session only among the live ones at a single instant: it is freed when its session exits, reclaimable by anyone afterwards, and auto-assigned as `<dirname>-<2 hex>` to every hand-started session. `ListAgents` returns every live session with its ref already resolved, and `peer.py` turned any of those names straight into a `uds:` socket — one command from a listing to a live send into a session the user was typing in. The skill said "never close a slot you did not spawn" five times over and had no equivalent rule for messages, keystrokes or screen reads. **This is a breaking change:** the ledger is now six columns with an `.owner` sidecar, and four-column ledgers are refused, because a row with no minted id cannot prove ownership of anything.

### Added

- **Ownership is minted, not looked up.** The supervisor generates a uuid and launches `claude -n <name> --session-id <uuid>`. A human never passes that flag, so a minted id can never select a hand-started session. The row goes on disk *before* the launch, which is what makes it a claim rather than an observation.
- **`lib/owned.py` — resolve a worker through the ledger, never through a name.** Distinct exit codes carry the part that matters: `0` ours, `1` no live session, `3` a live session holds this name and is not ours, `4` more than one answers. Only `1` improves by waiting; treating `3` as "not ready yet" is how a stop signal becomes a send to a stranger.
- **`lib/occupant.py` — a slot is not a session.** Every command that writes to a terminal takes a slot, consults no registry, and cannot say who is sitting in it. On the most ordinary sequence there is — worker exits, user starts their own `claude` in the tab — every locator still resolves, and the cleanup path reads `registry=gone` as "died mid-stage" and offers to close what is now the user's session. The join is the controlling terminal: the host names the tty, `ps` names the process.
- **`lib/me.py`** — this session's own name, `uds:` address and session id, replacing a 30-line heredoc. The third field is what the `.owner` sidecar records, and it is what lets a worker's reply be recognised as a reply rather than as a send to a stranger.

### Changed

- **`peer.py` keeps one job and loses the dangerous one.** It answers "is this name taken" for the pre-launch collision check and now **refuses to return an address at all** — a socket resolved from a name could belong to whatever session holds that name. It also sweeps every profile, because discovery is profile-scoped while the namespace and `SendMessage` are not: 15 live sessions across two profiles here, 9 visible from the default one.
- **cmux — an empty `--surface` is the caller's own surface.** `cmux read-screen --surface ""` printed the calling session's screen, and the resolver prints empty *exactly* when a worker's tab is gone, so the inline form delivered `down`+`enter` into the supervisor. `send`, `send-key`, `read-screen` and `close-surface` are now assign-and-guard, with an occupant check on each.
- **herdr — a second namespace the collision check could not see.** `herdr agent` spans 21 kinds and only `claude` ones reach the Claude registry, so a hand-started `codex` named `review-api` was invisible to the pre-launch check while every later `herdr agent …"$NAME"` resolved to that pane. It gets its own `herdr agent get` check, and a duplicate-name refusal is exit 1 — a hard stop, never one of the three classifier reissues.
- **The smoke test proves ownership.** New check 3b covers the `0/3/3/2` matrix and the enforcement hook; check 2's refused fixture is now the four-column one, since that is the format every earlier run wrote.

### Fixed

- **`/clear` no longer disowns a live worker.** It rotates the session id in place — same pid, name and socket, fresh id within 400 ms — so a pin on the id alone reported a healthy worker as dead the moment a user cleared its tab. The minted id establishes the binding; the pid, captured at readiness, holds it.
- **More than one match is refused rather than resolved.** `--session-id` reserves nothing: two live sessions were started with the same minted uuid and both registered, neither erroring. `peer.py` returned the first glob match, which is the shape that silently picks a stranger.
- **An empty `--session-id` is caught before the launch.** It exits 0 with a *random* uuid where a malformed one fails loudly, so a blank `uuidgen` produced a row naming an id no session would ever carry.
- **Teardown removes the `.owner` sidecar, not just the ledger.** Found by a live smoke run that had to delete it by hand.

## [0.6.3] — 2026-08-13 — "Holdout"

The same bug twice: a release measures something failing, fixes it in one place, and leaves the copies beside it teaching what it just disproved. v0.6.1 established that a worker must be handed the supervisor's literal `uds:` address — and the `SendMessage` template forty lines above that section, which is the copy-paste artifact a supervisor actually reaches for, went on saying "using the `from` address on it", as did the Rules summary and the ref-wall diagnosis. v0.6.2 proved that no cmux screen read reaches a Claude Code worker's history — and `hosts/cmux.md` §5 went on advertising its scrollback line as the way "for checking whether a worker's first reply was refused", the one question those 55 viewport lines answer cleanly and wrongly. Neither is a new defect. Both are the old one still standing exactly where a reader is likeliest to meet it, because a fix was filed as done when the section that explains it was written rather than when every copy of the superseded instruction was gone.

Both Fixed entries ship. The README changes are repo-level — visible to anyone reading the project, not part of the plugin payload — and the `/release` repair does not ship at all; it lives in `.claude/skills/`. All four are here because "which document says it" is what this release is about.

### Fixed

- **The `SendMessage` template no longer teaches the `from` address it was superseded by.** v0.6.1 measured that "reply to the `from` address on this message" does not hold — 2 of 2 workers addressed the supervisor by name anyway and were refused, the same ref wall as the 3 of 3 measured for workers told the name outright — and added the section requiring the literal `uds:` address in the task text. It did not update the three places that already carried the old instruction, and they are the ones a supervisor acts on: the template under "Send the task", which is that section's own copy-paste artifact and had not changed since v0.4.0; the Rules bullet, which is the summary, and which contradicted the "Address by `uds:`" rule four bullets above it; and the ref-wall diagnosis under "Watch", which named the `from`-address instruction as the fix for the failure the `from` address causes. All three now say what the section between them says, and the template gains a line pointing at `$ME` — the address to write into it is the supervisor's own, not the worker's, which is the one way to fill that field in wrongly while following every word of it.
- **`hosts/cmux.md` no longer offers a scrollback read as the way to check for a refusal, because on this host there is no such read.** v0.6.2 measured it against a worker with 120 uniquely marked lines and one real refusal behind it: plain, `--scrollback`, `--lines 40`, `--lines 200`, `--lines 600`, `--lines 2000` and `capture-pane` alike all returned **the same 55 viewport lines** and reached 47 of the 120 markers; `--lines` implies `--scrollback`, so they are one control and not two. The flags are not broken — the same surface after `/exit` dropped it to a plain shell returned 128 lines and all 120 markers on the first try. The cause is the alternate screen, which has no scrollback for cmux to read and which cmux has no command to scroll. That release fixed the smoke test's detector and shipped nothing else, so the one host that cannot answer a history question was still the one recommending you ask it. §5 now carries the measurement, states that no flag and no retry fixes it, and sends every history question to the transcript, which has neither a viewport nor a host in it. The core's screen-vs-transcript table said the two were equal places to look; it now says which to prefer and why, and that on one host the choice is not offered.

### Changed

- **The README shows the placement rule instead of describing it.** One recording per host running the *identical* three-agent prompt, so the difference is visible rather than asserted: cmux splits once and stacks three tabs in the new pane, herdr opens three tabs and never splits. Adds a "Why not just use subagents?" section — a comparison table, and the framing that subagents are the right default and this is for work a human wants a window into. Drops `docs/demo.gif`, which rendered `agent-toolkit:cmux-spawn-agent` — a skill name that has not existed since the host-file split, so the old clip was documenting a trigger nobody can type.
- **`/release` step 7 was split into one command per call, with a three-attempts rule — smoke-test-only, does not ship.** The v0.6.2 run of that step took **nine denials and zero real failures**: under `auto` mode the classifier denies a compound command as a unit, so `git checkout main && git pull` was denied while a bare `git pull` went straight through, and `git tag … && git push origin …` was denied while the bare `git tag` passed. Simple commands were denied too, and identical retries then succeeded — `gh pr merge` on the third attempt, `git tag` on the second, `git push origin v0.6.2` on the third. The step now issues one command per call and says to reissue an identical call about three times before recording a failure, because a denial and a failure are indistinguishable by inspection — a denied call never reaches the shell and produces exactly the empty output a real failure produces — and this is the one step past the last reversible act, where giving up early leaves the release merged and untagged.

## [0.6.2] — 2026-08-12 — "Plumb"

Two readings that came back clean and wrong, fixed the same way: stop reading the rendering and go down to the record underneath. A worker's reply address was resolved from the parent of the calling shell, which is the hosting `claude` only when nothing sits between them — and through a wrapper it did not merely come back empty, it came back naming **a real, unrelated live session on this machine**, socket and all. The smoke test's ref-wall detector read the worker's screen, and `cmux read-screen` cannot see a Claude Code worker's history at all, so it reported `refusals=0` over a refusal sitting right there in that worker's scrollback.

Neither failure has a symptom you could act on. One addresses a stranger and reports success; the other is a green check. Both were escalated by measurement rather than by reading — the address bug was found by feeding the old snippet a wrapper-sized pid and watching a stranger's name come back, and the screen bug by marking 120 lines and counting how many any flag combination could reach.

Only the first of the two ships. The second is smoke-test-only: it changes what the test can see, not what the plugin does. It is in this release anyway, because a test that cannot see a failure is indistinguishable from a plugin that does not have one.

### Fixed

- **The reply address is resolved by walking the process tree, not by taking the parent of the shell.** `ps -o ppid= -p` names the hosting `claude` only when it is the *immediate* parent. Measured 2026-08-12 in session `fixer-b2`, claude pid 27957: direct, the old form resolved correctly; through one `zsh -c` the parent was `/bin/zsh` and the result was empty. That used to cost a label — the snippet returned only a human-readable name — but it now carries the `uds:` address the entire reply instruction is built on, so an empty result leaves the supervisor falling back to the worker's *name*, which is precisely the ref wall the literal address exists to prevent. The failure reintroduces the bug two sections above it rather than degrading. **And empty is the good failure.** `sessions/<pid>.json` is keyed by pid, and pids recycle into exactly the range wrapper shells are born in: handed pid 19143, the old form printed `bin-09 uds:/tmp/cc-socks/19143.sock` in full — complete, plausible, and addressed to somebody else's live run. A worker given it reports its findings to a stranger, and nothing anywhere shows a fault. The walk returns the same answer at zero, one and two wrapper levels, only ever reads a record whose pid it has confirmed is a `claude`, honours every `CLAUDE_CONFIG_DIR` segment, refuses a record with no `messagingSocketPath`, and exits non-zero with a message on stderr on every branch — so an unresolvable address stops the run instead of producing a task with an empty one in it.
- **`cmux read-screen` cannot see a Claude Code worker's history at all, so the ref-wall check no longer asks it.** Measured against a worker with 120 uniquely marked lines and one real refusal behind it: plain, `--scrollback`, `--lines 40`, `--lines 200`, `--lines 600`, `--lines 2000` and `capture-pane` alike all returned the same 55 viewport lines and reached 47 of the 120 markers. `--lines` implies `--scrollback` — they are one control, not two. The flags are not broken: a control run in the same surface after `/exit` dropped it to a plain shell returned 128 lines and all 120 markers from the first one. The cause is that Claude Code runs on the **alternate screen**, which has no scrollback for cmux to read; herdr recovers history by scrolling the alt screen, and cmux exposes no command that does. So check 8's detector satisfied *both* of its PASS conditions — `refusals=0`, line count in the tens — while the ref wall sat in that worker's history: a false green of the same class as the hard-wrap bug fixed on the herdr side. The PASS condition now rests on the worker's transcript, which has neither a viewport nor a host in it — `SendMessage` `tool_use` blocks counted structurally, refusals read out of `tool_result` blocks. Calls and refusals together separate print-only (0/0), the ref wall (1/1) and a clean send (≥1/0); all three shapes were produced on this machine. A plain `grep` of the raw jsonl is not a substitute — it returned 4 against the same transcript's 1, the phrase being ordinary prose wherever anyone writes about the ref wall. Both hosts' screen reads are kept, demoted to diagnosis.

### Changed

- **Check 11 — the blocked-worker signals, exercised instead of asserted.** Check 5 proved `WARN` and check 9 proved `DONE`; `ASK`, `ATTN`, `CLEAR` and `GONE` had only ever been hand-measured. `ATTN` matters most: check 1d exists to prevent the permission-class mismatch that produces it, and check 8's no-reply diagnosis tells a reader to treat `ATTN` as "held, not lost" — a branch no run had ever made fire. Check 11 spawns its own worker with an explicit permission class into the already-trusted scratch repo, blocks it on a shell command, clears it, blocks it again on `AskUserQuestion`, and reads `status`/`waitingFor` from the registry both times — one `waiting` status routed to two different signals by a single substring test, observed going both ways in one run. Then it kills that worker with the watcher still armed, which is the only place `GONE` is ever observed: teardown stops every monitor first, so nothing is listening when a worker's slot closes, and two full runs closed four workers between them without producing one `GONE` line. Running the new check found its defects, all of them in its own prose — 11a directed the reader to launch into check 7's worker's pane, which herdr refuses with `agent_pane_busy` at exit 1 and which cmux would satisfy by typing a shell line into a running `claude`; the `waitingFor` exit-1 note gave one of that code's two meanings, since exit 1 is byte-identical for "not blocked yet" and "worker is dead", so `status` is read first (exit 0 means early, exit 1 means gone); and `ATTN` does not prove your command caused the block, because a held peer message parks a worker at the same `waiting` / `permission prompt` pair. `CLEAR` is honest about its limits: it needs a block that ends with no turn behind it, which the check cannot force, so 11c requires recording which of `CLEAR` or `DONE` appeared rather than passing on either. Teardown becomes check 12. Check 9 now warns that a fresh worker emits one `DONE` before any task is sent — its boot turn — which a supervisor could read as its own.

## [0.6.1] — 2026-08-12 — "Carve"

Three ways a supervisor can be told the truth by every signal it has and still be wrong. All three were found by running the smoke test rather than by reading it, all three are silent, and each is fixed by carving an exception into an instruction that was too broad — hence the name.

A task message can talk the worker out of replying. `SendMessage` is a tool call, so the natural way to keep a small task small — "do not read files, run commands, or investigate anything" — reads to a literal-minded worker as "do not use tools", and it satisfies "reply with one line and nothing else" by *printing* that line. Measured one in two. `CALLER_SLOT` never survived the `Bash` call that set it and could not be made to by exporting it, so every path keyed on the slot was quietly built from an empty string — including, at two sites, a `pgrep`/`pkill` pattern that then matched every watcher on the machine. And the reply address turned out not to hold: told to use the `from` address on the message they received, **0 of 2 workers did** — both used the supervisor's name, both were refused, both paid a round trip on the one message carrying their results.

None of the three has a symptom you can act on. A printed reply leaves a worker that looks finished from every angle. An empty slot produces paths that are wrong rather than absent, so nothing errors. A refused first reply succeeds on the retry, so the results arrive and only a grep of the worker's screen shows what it cost. What changed is not just the wording and the bindings but the diagnosis around each: every one now names the signal that separates it from the failure it resembles.

The measurements behind the reply address deserve their own line, because they are what a "verified" claim looks like when it is thin: `from` alone went 5 of 5, then 1 of 1 under herdr, then 0 of 2 across both hosts. It works often enough to look settled.

### Fixed

- **A task that forbids tools gets printed, not sent — and now says so.** The reply instruction carves the tool out of the prohibition explicitly ("you MUST deliver the reply with the SendMessage tool; printing the text as output does not count as replying"), caps the reply **body** rather than the worker's whole turn, and exempts the schema fetch that a deferred `SendMessage` needs first — replying costs two tool calls there, not one, and a worker told its "only action" is to reply can read the fetch itself as forbidden. Measured 2026-08-12: two workers sent the same probe under the old wording, identical but for their own names; one sent, one printed.
- **No watcher signal names a printed reply, so the trigger is now the missing reply itself.** `DONE` is a sampled `busy → idle` transition and a print-only turn is the shortest a worker can take, so it can open and close inside one poll — waiting for `DONE` before investigating is waiting for something that may never fire. The evidence is a `SendMessage` `tool_use` block; the `⎿ … → uds:` line is terminal rendering and is never in the transcript file, so a grep for it there returns nothing on a perfectly healthy send. A call whose result reads `is not an agent in this conversation` is the ref wall instead, whose fix is the `from` address and not a change to the prohibitions.
- **`export` does not carry `CALLER_SLOT` anywhere, and the skill no longer claims it does.** Measured 2026-08-12: an exported probe read back empty in the next `Bash` call *and* inside a `Monitor` command, while `$CMUX_SURFACE_ID` was visible in both. Every block that needs the slot now re-derives it from the host's own environment variable — the one thing that does survive — and refuses on empty. The `Monitor` command takes the slot written out literally, the way it already takes the plugin root.
- **An empty slot turned two scoped commands into machine-wide ones.** `pgrep -fl "watch-workers.py.*${CALLER_SLOT}"` collapses to `watch-workers.py.*` — precisely the bare form the paragraph beside it forbids, reached by accident rather than by typing it — and the remedy one line below, `pkill`, then reaps every other session's watcher including the supervisor's own. Both sites now bind and guard the slot in their own block.
- **A worker is told the literal `uds:` address to reply to, because "use the `from` address" did not hold.** Measured 2026-08-12 across both hosts, 0 of 2: each worker addressed the supervisor by name anyway, hit the ref wall, and recovered via the ref in the refusal. That is the same failure previously recorded for workers told to reply *by name* (3 of 3), reached from the opposite instruction — so the variable is not "name versus `from`". A worker holds several plausible ways to address a supervisor and `SendMessage`'s own guidance leans toward names; a literal address leaves nothing to choose. The skill already required exactly this of a supervisor addressing a worker, and the reply direction now matches it. The `from` sentence stays as a fallback.
- **A worker cannot look up the name it was launched with, so nothing asks it to.** Measured 2 of 2: both said so unprompted and both guessed — one inferred a name from the supervisor's socket path and the scratch directory, the other took a `ListAgents` row that belonged to a **different concurrent run**. A supervisor that wants a worker's identity in the reply body writes it into the task itself; otherwise the transport's `from-name` is authoritative and free.

## [0.6.0] — 2026-08-12 — "Compass"

A second terminal, and the discovery that supporting one is mostly a question of refusing to trust the other. **Breaking:** `cmux-spawn-agent` is now `spawn-agent`, and its bundled scripts moved under `lib/` and `hosts/`. The bare name is back because the host no longer belongs in it — `SKILL.md` names no terminal command at all, and one file per host holds every command, so a session reads the core plus exactly one host file. That split was worth doing for a reason the measurement made plain: of the 1164 lines that were "the cmux skill", only 259 were actually about cmux. The other 85% — the peer registry, `uds:` messaging, the watcher, permission classes, the ledger — is Claude Code, not a terminal, and under a second *skill* it would have been copied and left to drift. It costs a cmux session about 17% more text than before; that is the price of the host detection, the readiness rules and the traps below, and it is paid once rather than twice.

The headline is the precedence rule. herdr runs as a server and client, so its panes inherit the environment of whatever started the server — and when that was a cmux surface, every herdr pane on the machine carries a `CMUX_SURFACE_ID` that is not stale, not dead, and not harmless: it is the live surface displaying the herdr window, identical across every pane. A skill that checked for cmux first would aim every placement command at the herdr window and key every run's ledger to one shared file, with every command returning `OK`. So host detection is a precedence table where `HERDR_ENV=1` wins unconditionally, and "don't care" is written into the cmux column on purpose.

Both hosts were verified end to end by the smoke test before this shipped — a real worker spawned, gated, cleared, messaged, replied, reported and torn down in each — and those two runs found four defects that are fixed below.

### Added

- **`hosts/herdr.md` — herdr as a first-class host, measured rather than assumed.** Its topology is inverted from cmux's (a herdr tab contains panes; a cmux pane contains tabs), so the placement rule inverts with it: every worker gets its own tab, because there a tab costs the user nothing while a split pane measured ~28 columns and wrapped screen reads into ribbons. herdr also removes work — `--cwd` is an argv element, so the entire quoting failure class that cmux's `cd "$REPO"` lives with cannot occur; `herdr pane get` doubles as the liveness oracle, so herdr needs no resolver script at all; and `agent prompt` submits text and Enter atomically, expanding slash commands, where cmux needs `send` then a separate `send-key`.
- **A blocking wait on `blocked`, alongside the watcher rather than instead of it.** `herdr agent wait --until blocked` reached `blocked` in 3.9 s on a `manual`-mode worker, agreeing exactly with the registry's `waiting` / `permission prompt`. It does not retire `watch-workers.py`: nothing but the pid check reports a worker that *died*, and herdr's own `unknown` state explicitly proves neither completion nor death.
- **A documented contract for what a host must supply.** The core states the four properties any host's slot id must have — durable, unique per caller, filename-safe, non-empty or refuse — so a third host is a new file and a new row in one table, not an edit to the core.

### Fixed

- **Readiness is the registry, never the host's word for it.** herdr's `agent start` returns `interactive_ready: true`, `agent_status: "idle"`, exit 0, in three seconds — *for a worker parked on the folder-trust gate that has not registered at all*, reproduced twice. Believe it and the next call is worse than a lost task: prompting that worker sends an Enter that selects "Yes, I trust this folder", granting read, edit and execute in a directory the user never approved, swallowing the task text, and leaving a session with **zero turns** — proved by the absence of its transcript file. All three reported as success. The skill's own registry-based readiness loop is what catches it, so it now runs on every host regardless of what the host claims, and `esc` is documented as the safe out when the gate names the wrong directory.
- **Skill text no longer rewrites itself from its own arguments.** A skill invoked *with* arguments has every bare dollar-plus-digit in its text replaced by one of those arguments, zero-indexed, before the model reads a byte. Measured with a probe skill invoked as `/probe ZULU YANKEE XRAY WHISKEY VICTOR`, the awk field reference for column 4 was served as `VICTOR`. Two shipped occurrences — the ledger's own "what am I still owed?" query and cmux's pane-reuse scan — each becoming *valid* awk asking the wrong question, with no error anywhere. It fires only when a user passes arguments, so both behaved perfectly right up until someone typed the slash command with a sentence after it. Both now use `awk -v c=N`.
- **`herdr pane get` is unwrapped correctly at teardown.** Its payload is nested under `pane`; the shortened accessor raised `KeyError` on the *first* step of cleanup, which would have left the worker tab open and its ledger row unpruned. Caught by the first live smoke run.
- **Nothing waits on `idle` for a finished worker.** A worker whose tab nobody focused settles as `done`, not `idle`, so `agent wait --until idle` timed out on a worker that had already finished. Every worker this skill spawns is `--no-focus`, which makes that the normal case rather than an edge one.

### Changed

- **The screen-read model for herdr, corrected against a live run.** Claude Code runs on the alternate screen, and herdr recovers its history by scrolling — which it can only do while the agent is idle. So `recent-unwrapped` is a hard error while a worker is busy, and `visible` (which does work then) silently saturates at the viewport: measured against a worker that had emitted 120 marked lines, `visible` returned 46 matches at `--lines 200` and 46 again at `--lines 600`. Swapping sources to dodge the error returns a clean `0` from a grep that never read the line in question.
- **The smoke test covers both hosts**, detects which one it is in, and now proves its own plugin root rather than trusting a token — it resolves the root from `git rev-parse` and then requires a profile whose marketplace entry is a `directory` source pointing at this tree, because otherwise it would be measuring bytes no session reads. Its scratch repo is now unique per run: folder trust is recorded per path in `~/.claude.json` and **outlives the directory**, so a fixed path was gated on a machine's first run and silently pre-trusted forever after, quietly retiring the gate-clearing checks it exists to exercise.

### Removed

- **The smoke test no longer ships.** It moved out of the plugin into this repo's own `.claude/skills/`, so `/agent-toolkit:cmux-spawn-agent-smoke` is gone with no installed replacement. It tests the working tree, which under a `directory`-sourced install is exactly what every session loads; shipping 800 lines of maintainer tooling to every user bought nobody anything.

## [0.5.0] — 2026-08-09 — "Litmus"

v0.4.0 made the plugin prove itself once, by hand, against live workers. This release turns that into something anyone can re-run in five minutes. It exists because of an asymmetry v0.4.0 exposed: every cheap check in this plugin can pass while spawning is completely dead, since none of them touches a worker — and the faults that have actually shipped here converge on one symptom, a run that times out, which is not a diagnosis. The hard part turned out to be writing checks that cannot report FAIL for correctly-working code; two of them had to be rewritten to compare against `peer.py` and against the filesystem rather than against a literal string before that was true, and both of those are noted below because the same mistake is easy to reintroduce.

### Added

- **`/agent-toolkit:cmux-spawn-agent-smoke` — ten checks that make the machine prove `cmux-spawn-agent` still works.** One split, one worker, about five minutes. It is not a code review and does not read the skill for correctness: it spawns a real worker into a real cmux surface, asserts the worker landed in its own pane rather than covering the session the user is talking to, sends it a task at its `uds:` address, requires the reply to be accepted on the worker's *first* attempt, and then proves the teardown left no stranded tab and no orphaned watcher. Every check names the signal you read and what its failure means. The verdict is deliberately not a percentage: it has a **PARTIAL** grade reserved for the case worth naming loudly — the guards all holding while the live path is broken.
- **A staleness gate that runs before anything else.** Skill text is resolved once at session start and cached for the life of that process, so a session that started before the plugin changed will smoke-test bytes nobody ships — and report a clean pass for them. The gate compares the session's start time against the newest `SKILL.md` and refuses to continue when it loses; writing it caught the authoring session two and a half hours behind the text it was about to claim to test. It walks the process tree rather than taking the parent of `$$`, and that is not tidiness: through one wrapping `zsh` the naive form resolved a pid 2 h 38 m younger than the real session and flipped a genuine FAIL to PASS. Script mtimes are excluded on purpose — only `SKILL.md` is snapshotted, so including `peer.py` and friends would fail sessions that are perfectly current.
- **Two checks that compare against the machine, not against a literal.** The name-collision fixture picker mirrors `peer.py`'s own liveness predicate, because the obvious shorthand `os.kill(pid or -1, 0)` addresses every process the user may signal and answers yes — handing back a name that `peer.py` then correctly refuses, so the check would fail the guard it exists to confirm. The worker-cwd assertion uses `os.path.samefile` rather than string equality, because `$TMPDIR` ends in a slash and `/var` is a symlink to `/private/var`: a healthy run prints two visibly different strings for the same directory, so `==` would turn the one check proving this plugin's most-repeated bug is fixed into a guaranteed FAIL on every machine with a `$TMPDIR`.

## [0.4.0] — 2026-08-09 — "Shakedown"

v0.3.0 was written from reading the machinery. This release is what happened when the plugin was made to prove itself: real agents spawned into real cmux tabs and driven to completion, with every claim in the skill checked against a live worker. Almost nothing failed loudly. The watcher deleted a worker's remembered state on a microsecond-wide race and swallowed its `DONE` permanently; a repo path containing a space died before `claude` ever started and looked exactly like a slow boot; the name-collision check reported 6 of 7 live session names as free; and the documented rescue for a worker stuck at the folder-trust prompt sent the keystroke that terminates it. Every one of those reads as a healthy run right up to the moment you need it not to be, which is why they survived three releases. Everything below was measured, not inferred.

### Added

- **A sixth watcher line, `WARN`.** A watcher armed on a ledger that matches no live session used to run forever in total silence — indistinguishable from a healthy watcher whose workers are simply still busy, which is the one thing a supervisor cannot afford to confuse. It now says so once, after a 30-second grace, naming which case it is: unreadable ledger, empty ledger, or rows matching no live session. `WARN` names no worker and is explicitly not a worker signal. The grace is not zero because a ledger row is written *before* its worker is launched, so "no match yet" is the normal state while a `claude` boots.
- **A guard against a stale ledger.** The ledger path is keyed by the cmux surface uuid, which outlives any one `claude`, so relaunching in the same tab silently inherits the previous run's rows — and a ledger left in the pre-0.3.0 format makes the watcher permanently deaf with no error at all.

### Fixed

- **A torn registry read no longer swallows a `DONE`.** Records are rewritten in place, so a reader can catch one mid-write. That parse failure was treated as an absence, which emitted a false `GONE` and — the real damage — deleted the worker's remembered state, so a worker that finished during the gap lost the one signal it cannot resend. A failed parse is now retried once and then treated as *no information*, holding the prior state; only a genuine absence counts toward death, and death now needs two consecutive misses. The window is real on both runtimes and much wider on one: under bun a shortening write leaves valid JSON plus a stale tail for ~0.65 µs, while under node `O_TRUNC` leaves the file genuinely empty for ~11 µs on *every* write, roughly 45× more exposed.
- **A worker killed mid-write is no longer immortal.** Holding state on an unparseable record, done naively, means a file that never parses again never fires `GONE` either — and `SIGKILL` skips the handler that would unlink it, so the corpse stays torn on disk forever. Resolved by taking the pid from the registry filename, the body being unparseable by definition on that path, and degrading a permanent tear from a live process to an absence.
- **A repo path containing a space no longer kills the launch.** The launch line did not quote it, so `cd` failed before `claude` started — and in zsh the message is the baffling `string not in pwd`, not an argument error. The only symptom was the readiness loop burning its full 60 seconds.
- **The name-collision check asks for the name, not the address.** It asked for a worker's messaging address, which returns the same "not found" answer for a live session that simply has no socket. On the test machine that reported 6 of 7 live session names as free.
- **Clearing a startup gate no longer terminates the worker being rescued.** The instruction pointed at a worked example that sends `down` then `enter`. On the folder-trust dialog option 1 is already selected and option 2 is "No, exit". Both gates are answered by `enter` alone.
- **The reply guidance was backwards.** Telling a worker to reply to the supervisor's *name* had its first message refused 3 times out of 3; telling it to reply to the `from` address on the message it received was accepted 5 times out of 5. The accompanying claim that the ref wall is one-sided was also false — the wall is bidirectional, and only the recovery is one-sided.
- **The fan-out loop wrote its ledger row after launching**, contradicting the single-agent path and the skill's own stated reason for the ordering. It also wrote a row when the surface could not be resolved, producing a row whose columns shift left when read back — so a real open tab could never be offered for closing.
- **The documented ledger prune was wrong in both directions**, at different times: joined with `&&` it silently did nothing on the last row, because `grep` exits 1 when it selects nothing; joined with `;` an empty or unset `$su` wiped the entire ledger and exited 0. It is now guarded, with both failure directions written down.
- **A bad poll interval prints the usage message.** It was parsed at import time, sixty lines before the argument check could reject it, so the usage text the script already contained was unreachable and the user got a traceback in the supervisor's notification stream instead.
- **Tearing down the `Monitor` no longer looks like a crash.** `SIGPIPE` is handled, so the watcher dies quietly like any other filter rather than printing a `BrokenPipeError` at interpreter shutdown.
- **`peer.py` no longer accepts an empty `CLAUDE_CONFIG_DIR` segment.** A trailing or doubled colon — what a shell hook appending a profile path produces — degraded its glob to a relative path read from whatever directory the caller happened to be standing in.
- **Closing down no longer manufactures a burst of `GONE` lines.** The finish sequence now stops the watcher first; the old order guaranteed the noise on every close.

### Changed

- **The folder-trust gate is documented.** It holds a worker *before* it registers, even in a plain git checkout under default permissions, which makes it invisible to every signal the skill provides. Reading the worker's screen on a readiness timeout is therefore now mandatory rather than advisory — an unquoted path and a gate produce an identical signature, and only the screen tells them apart.
- **Several claims corrected where measurement disagreed with them.** A ref is not obtainable only from `ListAgents` — the refusal itself prints it. Refs are not re-enumerated by a close; the echoed number is an unrelated allocation counter. The extra `pgrep` match is the watcher's own `zsh -c` host shell, not the shell running the check. A write does not reliably provoke a permission prompt under `auto`. And the cwd verification is self-concealing when the target repo is the caller's own cwd, which it now says.
- **README described the pre-0.3.0 design** — an event-bus filter emitting an `EXIT` token, a ledger column that no longer exists, and a session id assigned before launch as the join key. It now describes the peer-registry poll, its actual signals, and the name.
- **`CLAUDE.md` records that skill text is cached per process.** It is resolved once at session start, and subagents inherit their parent's snapshot — so a session cannot verify its own edits to a skill, and only a `claude` started after the edit loads it. Verified 2026-08-09: a subagent in a process started before the edit was served the pre-edit text with all seven markers absent, while a worker spawned into a fresh cmux tab after it was served the post-edit text with all seven present — same tree, same install, same moment. The structure diagram also still called the watcher a stdin filter and omitted `peer.py` and `surface.py`.

## [0.3.0] — 2026-08-09 — "Switchboard"

Claude Code 2.1.224 gives every session an inbox socket and a record on disk, and between them they replace both halves of this plugin's machinery. A worker is now addressed and reports its findings over cross-session messaging, and its state is read from the peer registry instead of parsed off cmux's event bus. The gain that matters is the case the bus could never cover at all: a worker that is killed runs no hook and publishes nothing, so it used to look exactly like a worker still working — which is why the two commits that landed after v0.2.0 were both about the watcher failing to say anything.

### Added

- **Workers report their findings in a message, and it arrives before the watcher notices.** A stage's outcome now interrupts the supervisor with the result in it, instead of being dug out of a transcript. Ask for the findings, not an acknowledgement — a reply saying "done" wastes the round trip.
- **`peer.py` and `surface.py` ship as files.** Name to socket address, status, cwd and session id; surface ref to uuid and back, plus pane and tty. They were shell functions in the draft, which quietly failed: every Bash call is a fresh shell, so a function defined once and used ten sections later asks for its whole definition again every time.
- **A fifth watcher signal, `CLEAR`.** A worker that stops being blocked without a turn running has nothing to collect, and saying so is what keeps `DONE` meaning what it claims.

### Changed

- **The watcher polls the peer registry instead of the cmux event bus**, and drops from 230 lines to 133 — no bus frames, no request-id de-duplication, no timing-collapse window, no `PreToolUse` fallback. It also no longer depends on cmux at all.
- **`EXIT` became `GONE`**, and now covers every way a worker stops running rather than only the graceful one. The `EXIT` shipped after v0.2.0 could not fire for a killed worker, because the signal is uncatchable at the source; polling process liveness has no such blind spot.
- **The launch name is the only join key.** No `--session-id`, no `uuidgen` — one string is the tab title, the registry key and the message address.
- **The skill documents the two channels as non-interchangeable.** Messages cannot clear a block or run a slash command; keys can do both. Both were measured, not assumed.
- README carries a 3× demo GIF of spawning three agents.

### Fixed

- **`DONE` no longer fires for a worker that did nothing.** Leaving a block counted as a turn ending, so a terminal overlay opening over an idle worker produced a completion for a session whose transcript never gained a record. `DONE` is now strictly working-to-idle.
- **An unknown `status` no longer swallows a turn end.** The field is open-ended — a supervisor was caught reporting `shell` — and keeping each unseen value as a state of its own stopped the transition out of it from being recognised.
- **Liveness no longer answers "alive" for every dead worker.** The registry file outlives the process, and the pid fallback was `os.kill(-1, 0)`, which addresses every process the user may signal and succeeds.
- **The ledger row is written before the worker is launched**, as the prose beside it always said; the code did the opposite, leaving a window where a live worker had no ledger entry.
- **A worker suspended on a question is reported as `ASK`.** A question suspends the turn rather than ending it, so a watcher listening only for endings was deaf to the single most common reason a worker needs a human — and a deaf watcher looks exactly like a worker still working.

## [0.2.0] — 2026-08-07 — "Summons"

A demo prompt short enough to be worth showing kept opening no tabs at all. The skill was not failing to match — it was matching the same ground the built-in subagent tool already owns and losing the tie, because "run several agents in parallel and report when they finish" describes a subagent perfectly. The only way to win was to say "in cmux tabs" out loud, which is precisely the detail a showcase should not have to spell out.

### Added

- **The word "spawn" is now a sufficient trigger on its own.** No mention of cmux, tabs or panes is required: `Spawn 3 agents: echo "ping", argue the Earth is flat, write a haiku. Report each as it lands.` routes here. The description also states outright that this is preferred over the built-in subagent/Task tool, which is the part that actually breaks the tie — a subagent is invisible and cannot be watched, clicked into, or taken over, which is the whole point of spawning one. A Rules entry backs it up for the case where the skill is already loaded and the tasks look small enough to be worth downgrading.

  The claim is deliberately narrow. Only "spawn" is taken; "run", "start" and "in parallel" stay with subagents, because a request that genuinely wants an invisible agent reads as "research X" or "look into Y" rather than "spawn one".

### Changed

- **Documented the frontmatter trap this release nearly shipped.** A `": "` inside a skill `description` ends the plain YAML scalar and the block fails to parse — and the failure is silent at runtime: the skill loads with empty metadata, every field dropped, so it never triggers again while nothing in its text looks wrong. Worse, the marketplace-level `claude plugin validate .` does not read skill frontmatter and passes happily; only `claude plugin validate ./plugins/agent-toolkit` catches it. Both are now written down in `CLAUDE.md`.

## [0.1.4] — 2026-08-06 — "Sentry"

The skill was smoke-tested end to end against live cmux surfaces for the first time. Every mechanism held — one split with three tabs inside it, `DONE`, `ATTN` and `EXIT` all observed on the wire, a worker spawned after the watcher was armed picked up from the reloaded ledger. What did not hold was the order the walkthrough puts them in: read top to bottom, it starts the work before anything is watching it.

### Fixed

- **The walkthrough never armed the watcher.** "Spawn one agent" ran from the ledger row straight to "only now send the task", and the `Monitor` appeared two sections later, under "Wait for a stage to finish" — a heading you reach only once the task is already running. The instruction to arm first existed solely in the Rules at the very bottom, so the body and the rules disagreed about the one step whose entire value is its timing. Arming is now a numbered part of the walkthrough, between the ledger write and the send, where the reader is already standing.
- **Nothing said the watcher block is the `Monitor` tool.** It was presented as an ordinary shell pipeline, which makes `Bash(run_in_background: true)` look like the same thing done more cheaply. It is not: only a `Monitor`'s stdout lines become notifications, a backgrounded `Bash` notifies once *on exit*, and `--reconnect` guarantees this pipeline never exits. Every `DONE` then lands in an output file nobody reads while `pgrep` shows a perfectly healthy watcher — the same silent deafness the ledger-path and timestamp warnings already existed to prevent, arriving through the one door they left open.
- **The registration wait was unbounded.** `until claude agents --json | grep -q "$SID"; do sleep 1; done` has no exit for a launch line that never started `claude` — a typo, or a `cd` into a directory whose profile lacks it. It does not fail, it spins until the harness SIGKILLs the whole call with the ledger row already written and the task never sent, which afterwards is indistinguishable from a worker that simply did nothing. It now gives up after 60s and says so.

## [0.1.3] — 2026-08-06 — "Scoped"

Two guarantees from the last release turned out to be advice rather than mechanism. A warning you have just read does not stop you making the mistake, and a check that lists every process on the machine is not a check.

### Fixed

- **The `cd` is now guarded, not merely warned about.** Two agents in a row dropped `cd <repo>` from the launch line despite the bolded paragraph saying it is not optional — the second immediately after quoting that paragraph back. The mitigation was attentional ("read the launch line back before sending it") and there was nothing to compare it against. `REPO` is now a variable in the anchor block, guarded alongside `$CMUX_WORKSPACE_ID` and `$CMUX_SURFACE_ID` and refusing anything without a `.git`, so an unset repo fails loudly at the guard instead of silently landing workers in the caller's cwd — where it only misbehaves when the caller happens to be somewhere else, which is what makes it so hard to notice.
- **The orphan-watcher check implicated everyone else's runs.** It said "kill only your own — the ledger path tells them apart" and then printed `pgrep -fl watch-workers.py`, which lists every watcher on the machine wrapped in 400-character shell preambles. An agent following it reported two healthy watchers as orphans, one of them its own supervisor's live Monitor. The check is now scoped to `${CMUX_SURFACE_ID}`, turning it from a reading exercise into a yes/no, and a watcher is only reapable once `ps -o ppid=` shows the `claude` that armed it is actually gone.
- **Cleanup had no stated order.** Closing surfaces, deleting the ledger and stopping the watcher lived in three separate places, and the sequence mattered: stopping the watcher before deleting the ledger leaves a window in which a late event names a worker already reported. It is now four numbered steps in one place. The anchor block also `touch`es the ledger, so a first run stops printing "no such file" to stderr and teaching readers to ignore it.

## [0.1.2] — 2026-08-06 — "Reaper"

The cleanup section treated closing the tabs as the end of a run. It isn't — the watcher is a process, and nothing was stopping it.

### Fixed

- **The PR-scope check printed help text instead of a diffstat.** The merge gate added in v0.1.1 called `gh pr diff --stat`, and `gh pr diff` has no `--stat` — it accepts `--patch`, `--name-only`, `--color` and `--exclude`. Passing an unknown flag prints usage and exits 0, so the step looked like it ran while showing nothing, and the approval it exists to inform was back to being uninformed. It now uses `git diff --stat main...HEAD` (three dots, against the merge base) plus a `gh pr view` count. Caught by running the step on this release rather than by reading it.
- **A spawned agent's watcher outlived the agent.** A `Monitor` armed with `persistent: true` runs until `TaskStop` or the end of the session that armed it, and a *spawned* agent's session ending does not reap it. Observed live at the end of a six-agent run: one agent had finished, its surface was closed and its ledger deleted, and its watcher was still streaming the global event bus. The cleanup section closed surfaces and pruned ledger rows and never mentioned the process. It now ends by stopping the watcher and checking `pgrep -fl watch-workers.py` for orphans — matching only your own, since another live run's watcher is indistinguishable except by the ledger path in its command line. Deleting the ledger file (not just its rows) is what makes a survivor harmless: a watcher whose ledger is gone matches no session id and reports nothing.

## [0.1.1] — 2026-08-06 — "Backstop"

Both shipped skills claimed guarantees they did not deliver, and this release closes the gap in every case rather than softening the claim. `cmux-spawn-agent`'s mandatory watcher was silently deaf, its guard checked the wrong variable, and its pane reuse could split into a dead tab; `/release`'s staging gate was advertised as making a half-applied release impossible while being structurally blind to the failure a broken `regex` entry actually causes. Nothing here changes what either skill is for — every change makes an existing promise true.

### Fixed

- **The mandatory worker watcher was totally deaf.** `watch-workers.py` returned a constant `0.0` when `occurred_at` was missing or unparseable, so the collapse window compared `0.0` against `0.0` and swallowed every subsequent event for that key — three real turn-ends produced zero output. Timestamps now fall back to arrival time on the same epoch scale, so an event without a parseable `occurred_at` is still reported.
- **Waiting on a single worker no longer takes a different code path.** The one-worker shortcut grepped `agent.hook.Stop` straight out of the stream, so it could not see `PermissionRequest` or `SessionEnd` — a blocked worker and a dead one both read as still working — and it relied on `grep -m1` ending the pipeline, which does not happen until the stream's next write. One worker now gets the same Monitor and the same ledger as ten.
- **Pane reuse could resolve to a dead pane.** Only the ledger's last row was consulted, so closing the newest tab sent the next spawn into a pane that no longer existed and split a second time. Every row is now scanned newest-first for a live pane. The workspace guard also refused only on an empty `CMUX_WORKSPACE_ID` while placement passes `--surface "$CMUX_SURFACE_ID"` and the ledger is keyed by it — the guard now checks what is actually used.
- **`/release`'s staging gate only looked for leftovers.** A Release Files entry that step 3 never rewrote — precisely what a failing `regex` entry produces — passed a clean tree unnoticed. The gate now also asserts every path from the block is staged, and reads `git status --porcelain`'s second column so a re-edited `MM` file stops slipping past a `' M'` scan. It runs between `git add` and `git commit`, while the tree is still recoverable, instead of after the half-applied release had already landed.
- **A release could land merged and untagged.** An explicit `X.Y.Z` that was already tagged failed only at step 7, after `gh pr merge`, poisoning the next release's "since the last tag" window; the tag is now checked free before anything is written. Declining the merge had no documented exit, so a re-run double-bumped and wrote a second CHANGELOG entry — there are now three named exits. An aborted run leaving exactly the release files dirty is no longer refused as a dirty tree, which had made the documented recovery unreachable.
- **The README's `Latest:` line described the previous release.** Its pattern captured only the version digits, so a bump left the codename and summary stale; it now spans the whole line and substitutes all three named groups, anchored so trailing text is a non-match rather than a silent truncation at the first close-paren. Every Conventional Commit type also has a CHANGELOG bucket now, and the manifests re-validate after the rewrite instead of only before it.

- **The merge approval was being asked for a diff nobody had seen.** Step 4 shows the release rewrite — four files, ~20 lines — and step 6 then opened a PR carrying the entire `$LAST..HEAD` window, eight files and some three hundred lines, while its body described only the CHANGELOG entry. The prompt that actually ships a release was the one with the least context behind it. Step 6 now prints `gh pr diff --stat`, states the real commit and file count in the prompt, and says plainly that this is not the diff approved a moment ago. `gh pr create` also pins `--base main` instead of inheriting the repo default, and silence is now explicitly treated as `n` rather than being an unhandled state in a skill otherwise fastidious about them.

- **The watcher command silently filtered out every worker when copied as written.** Its last argument was `"$LEDGER"`, a variable assigned in some earlier shell — and `Monitor` runs the command in a shell of its own, where it expands to nothing. The watcher then `stat`s an empty path, reads zero ledger rows, and discards every event as unknown: a watcher that runs happily and reports nothing, indistinguishable from a run where nothing has finished. The block now spells the path out from `$TMPDIR` and `$CMUX_SURFACE_ID`, which *are* in that shell's environment. Found by an agent following the skill literally, which is the only way this surfaces.

### Changed

- **`git checkout` is documented as this repo's deployment command.** A `directory`-source marketplace reads the working tree at skill-load time, so whichever branch is checked out here runs in every session in both profiles — user scope means unrelated projects too. Verified by probe sessions loading text byte-identical to a test branch's tip while `claude plugin list` reported a clean `0.1.0` pinned four commits behind `HEAD`. The version string is not evidence of what is loaded.
- **`cmux-spawn-agent`'s Rules say where the ledger lives.** The section told you to mark a row reported without naming the file — the one thing a context-less turn needs. `CLAUDE.md` also stopped duplicating the bump table it had already drifted from, and no longer promises that any new Release Files entry is picked up when only three `kind`s are implemented.

## [0.1.0] — 2026-08-06 — "Surface"

Initial release. The `spawn-agent` skill moves out of a dotfiles-and-symlinks arrangement into a versioned plugin, and gains a host prefix so the marketplace stays open to non-cmux agent skills.

### Added

- **`/agent-toolkit:cmux-spawn-agent`** — spawn Claude Code agents into cmux surfaces and drive multi-stage pipelines across them. Assigns each worker's session id before launch, which is the join key to its registry status, its notifications, and its transcript. Places workers as tabs in a single agents pane (one split per run, at most), anchored on the caller's own workspace and surface rather than on whatever is focused. Waits by push — a `cmux events --category agent` stream filtered through the bundled `watch-workers.py` against the run's ledger — with a documented polling fallback for answers needed inside one turn. Keeps a per-caller TSV ledger so an interrupted run can still answer what it owes, and offers (never performs) cleanup of only the surfaces it opened.
- **`watch-workers.py`** — stdin filter over the cmux event bus that emits one line per worker turn end (`DONE` / `ATTN` / `EXIT`). Filters strictly by the ledger's session ids, because the bus is global across workspaces and config profiles — an unfiltered watcher fires on the user's own tabs and on the orchestrator's own turns. Collapses the four frames cmux delivers per turn end into one, and re-reads the ledger on change so workers spawned after the watcher was armed are picked up without restarting it.

- **`/release`** — this repo's own release ceremony, as a repo-local skill. Derives the bump from the Conventional Commits since the last tag, rewrites every file declared in `CLAUDE.md`'s `## Release Files` block (rather than a list hard-coded in the skill), shows the diff, commits, opens a PR, and asks a *second* time before merging. Ends by refreshing both local profiles — necessary because the plugin payload cache is keyed by version string, so an unbumped edit never reaches an installed profile.

### Changed

- **Renamed `spawn-agent` → `cmux-spawn-agent`.** The skill is bound to cmux's surface/pane model and its event bus; the prefix says so, and leaves the bare name free for a host-agnostic successor.
- **Bundled-script path is now `${CLAUDE_PLUGIN_ROOT}`-anchored.** The watcher was previously invoked through `<skill-dir>`, the base directory printed at skill load. The plugin-root token resolves wherever the plugin was installed from, so the pipeline no longer depends on that line being read correctly.
- **Profile guidance generalized.** The "two profiles" section described one specific dual-profile setup; it now describes the general case — `claude agents --json` reads only the active `CLAUDE_CONFIG_DIR`, so a supervisor watching one registry reports workers in another as gone.
